住院首次病程记录智能生成

2026-11-19
技术分享
Word count: 5.3k   |   Reading time≈ 21 min

这篇博客完整记录我们参加”临床智录”赛题的项目 Clinical-Entry-agent：用大模型（qwen3.8-27b）读取入院资料片段，自动生成住院首次病程记录草稿。项目从 11-06 起步到 11-15 收官，历时约十天，最终在 1337 例真实病历的全量压测中拿到 96.7% 的成功率。本文从输入输出协议、流水线代码、校验器实现、数据转换到最终效果逐层展开。

仅用于教学比赛与评审，不用于真实诊疗。文中所有病例数据均为虚构/脱敏的教学数据。

1. 任务与协议

系统读取赛方 input.json，逐例调用 Chat Completions 兼容接口，写出 output.json。输入长这样（真实测试集 REAL-0169，一例胸腔积液病例）：

每个病例就是若干带编号的原文片段 + 一个资料截止点。输出则是结构化 JSON：三段正文（病例特点 / 拟诊讨论 / 诊疗计划）+ 依据说明 evidence + 待核事项 review_items：

注意 evidence 的两级设计：fact 是资料原有事实，inference 是基于资料的推断——不允许把推断伪装成事实。每条还绑定 source_ids，可以逐条回溯到原文片段。

赛题红线决定了整个系统的性格：

  • 只用截止点及此前的资料，不引入后续诊断/检查/结局
  • 数值、单位、时序、否定关系一字不差；不把”未提供”写成”正常”
  • 不把计划写成已实施
  • 输出条数与顺序恒等于输入，失败记录不隐瞒
  • 无密钥启动、不发 Authorization 头、模型名与地址只从 .env 读

一句话概括：宁缺毋假。这套约束后来全部落在校验器里。

2. 整体架构

三模式固定编排

按内容策略和单例 API 配额，流水线有三种模式：

模式 调用次数 内容 触发条件
baseline 1 v3 分层规则单发 performance 策略（默认）/ 配额不足
extract_enhanced 2+1 事实抽取 → 分析 → 终稿 quality 策略且配额足够
full 2+1 上者 + 本地参考区间查表注入 stage2 quality 策略且配额充足

模式选择就是一个纯函数，src/budget.py：

中间 stage 失败不重试，直接降级为单发 baseline（记 degraded=True + 原因）；降级后仍失败才记 failed。降级不是静默兜底，一切留痕在 run_log.json。

staged 流水线的第一环：事实抽取

full 模式的 stage1 是一个独立的”抽取引擎”角色，它的 system prompt 值得全文贴出，因为它把 LLM 应用开发里最容易被忽视的一条原则写到了极致——先冻结事实，再做推理：

抽取产出 key_facts / lab_values / negatives / missing_items / timeline 五类结构，stage2 的临床分析只能基于这份”冻结的事实清单”进行，stage3 终稿再继承 v3 的全部写作规则。拆成三环的收益很直接：每一环的错误可以被单独定位——数值失真找 stage1，鉴别诊断跑偏找 stage2，文风问题找 stage3。

本地参考区间查表（full 模式专属）

stage1 抽出的检验数值会先在本地查一遍参考区间表（不消耗任何 API 调用），把”偏高/偏低/正常”作为内部提示注入 stage2：

单位归一化是这个模块的主要工作量（μ/µ 微符号统一、X109/L→10^9/L 变体、大小写 /l→/L）。查不到的项一律返回 unknown 而不是猜——缺项、多义或非数值输入都不得臆测。所有条目 verified=false（待医学顾问核对），因此有一条硬规则：区间结果仅供模型内部排序，禁止把参考区间写进正文。

3. 校验器：项目的核心资产

src/validator.py 有 1251 行，比流水线本体大三倍——这不是失控，而是刻意的：**这个项目的难点从来不是”让模型写出来”，而是”证明它没瞎写”**。

设计原则写在模块 docstring 第一句：只报告问题，不改写正文。14 条规则按处置级别分四档：

级别 规则举例 处置
blocking schema（缺段/空正文/evidence 类型错） 直接 failed，不重试
hard numeric_fabrication / unknown_source_id / plan_implemented / definitive_diagnosis 默认 failed（宁缺毋假）
fixable missing_info_rewrite / summary_missing / enumerated_body / text_too_short 带反馈重试 1 次
warning text_too_long / 弱表述已修复等 仅入账

数值回溯：最难的一条规则

numeric_fabrication 要求三段正文里的每个”数值+单位”都能在原文 sources 中找到，否则判为疑似虚构。听起来就是一条正则的事，实际写成了这样：

每一个分支背后都是一例真实误杀（详见第 6 节踩坑实录）：中文数字”两周”被规范成”2周”、OCR 错字 ALTl80U/L（字母 l 混进数字 1）、项目名粘连 C30.4g/L（实为 C3=0.4g/L）、血压对不带单位 BP 180/120、并列枚举 Apgar 评分 4、6、8 分……这些全是 1337 例真实数据压出来的形态。

带反馈重试：fixable 的出路

校验发现 fixable 缺陷时，不是简单重掷骰子，而是把缺陷清单变成下一轮对话的反馈，src/pipeline.py：

build_retry_feedback 把每条缺陷格式化成 - [rule] message 列表拼进去。这相当于给模型一次”带着批改重写作文”的机会，实测对收束句缺失、列点腔这类格式问题的修复率很高。

红线单一来源

这是我最想安利给别人的一个设计。禁词表、参考区间、校验规则共享同一份定义，提示词通过占位符把它们注入给模型：

校验器 _check_implemented 用的也是同一个表。这样保证”写的约束 = 查的约束”，永远不会出现”提示词没禁止但校验器判死”的孤儿错误。

5. 数据集转换：把真实病历变成 input.json

导师提供了 1337 例中文真实病历（condition/diseases/analyses/diagnoses 字段），要拿它当测试集，得先转换成赛题的 sources 格式。转换同样用 LLM 完成，但配了一道数值保真校验和一层机械兜底，dev/convert_dataset.py：

流程：一例一次调用 → 提取原文全部数字集合 → 校验转换结果是否一个不少 → 失败带 hint 重试一次 → 仍失败直接用 mechanical_sources 逐字拼接兜底。金标准（diseases/diagnoses）独立存放，绝不进入 sources，防止答案泄漏。最终 1337/1337 转换成功，保真审计 0 例缺失。

6. 全量测试结果

full 模式、4 并发、错峰 2.5s，通宵跑完 1337 例：

指标 数值
成功 / 失败 1293 / 44（96.7%）
降级 3 例
API 总调用 5319 次（均值 3.98/例）
单例耗时 中位 101.3s，p90 124.2s
正文长度 中位 830 字（赛题建议区间 800–1600）
金标准病种覆盖 均值 0.819，中位 1.00

44 例失败全部是硬缺陷拦截或小模型 JSON 输出故障，无链路级错误。其中 35 例 NUMERIC_FABRICATION 经逐例复盘：19 例是模型真实错配（把”近 3 年夜尿增多”写成”3 天”、把年龄 20 写成”20%”），16 例属校验器盲区误杀——模型其实写对了，但回溯提取器没能匹配回原文。这个 19:16 的比例很能说明问题：剩余失败里将近一半仍然是模型的锅，另一半是评测系统自己的锅。

7. 踩坑实录：真实数据压出的迭代

每一行都是”上线前觉得不可能，上线后发现天天发生”：

# 问题 后果 修复
1 字母紧挨数字的单位（WBC8.46×109/L） 如实复述被判数值虚构、整例误杀 前导断言放宽 + X109/L 变体 + 血压斜杠对
2 编号列点腔（”1. 患者老年男性，2. ……”） 一眼 AI、个体化丢分 提示词 v4.2.0 自然段硬规则 + enumerated_body 可修复校验
3 “24小时尿蛋白定量”被当时间值回溯 合理计划被硬拦 检查专名豁免
4 兜底模板写出”0岁” 荒谬开头 age 0/None → “年龄未提供”
5 病史字段无归宿，致 121 例数值缺失 资料事实丢失 四段结构 + payload 补齐
6 思考模式 token 黑洞 单例 130–195s 双通道关思考，降到 20–40s
7 项目名粘连 C30.4g/L 复述被判虚构 _fusion_variants 剥离已知项目名前缀数字
8 中文数字”两周”→”2周” 规范化写法被判虚构 _cn_numeral_to_arabic 提取前归一
9 OCR 错字 ALTl80U/L 模型读对反而”对不上原文” 紧贴单位的 l/I/O 产出还原变体
10 全角符号 BP 165／100mmHg 提取失败 NFKC 半角化

两个反直觉的教训值得单独说：

其一，校验器的 bug 会以”模型质量差”的面目出现。 那 35 例”数值虚构”如果不逐例复盘，就会永远躺在”模型不行”的账上；实际 16 例是我们自己的提取盲区。每个修复都在 tests/test_real_units.py 里锁了一条回归用例（注释直接写着实例编号，如 REAL-0012、C30.4g/L → (0.4, "g/l")）。

其二，硬规则本身可能是错的。 “正文不少于 800 字”最初是硬约束，结果 555 例资料本来就薄（sources < 500 字）的病例因此多花一次重试调用，而且逼凑字会诱导编造——恰恰违背”宁缺毋假”。改成资料过薄时只记 warning 不触发重试（text_short_thin_source 规则），成本和幻觉一起降。

8. 最终效果长什么样

tools/review_report.py 把 input + output 渲染成自包含的 HTML 对照页：左边是赛方资料片段（带 S01–S04 徽标），右边是系统生成的三段正文、依据说明、待核事项，数值高亮、evidence 可点击跳转来源。下面是真实病例 REAL-0635（慢性咳喘 20 年伴心衰体征）的成品截图：

看几个细节就知道质量如何：

  • 拟诊讨论同时给出了恶性心源性与结核性两条鉴别路线，支持点/不支持点各归其位，结尾落在”待查”而非确诊；
  • 资料 S02/S04 大面积”未提供”，正文如实保留并转化为 3 条具体的待核事项，而不是编一份既往史出来；
  • 每条依据都能点开对应 source_id，fact 与 inference 分色标注。

提示词演进也值得一提——v2 只有基础角色 + 三段结构；v3 加入”具体程度阶梯”（每句写之前先判断这句话属于资料直接支持、可归纳、需标注推断、还是该进待核清单）；v4.1 根据 1337 例词频分析加了项目名限定词规则（糖化血红蛋白≠血红蛋白）；v4.2 用自然段硬规则消灭编号列点腔。每一版的变更都由数据或反馈驱动，没有一拍脑袋的改动。

9. 局限

诚实列出还没解决的事：

  1. 参考区间 27 项全部 verified=false（待医学顾问核对），目前仅用于内部推理提示，禁入正文
  2. 单例耗时预算只是事后告警，不强制中止（等主办方公布正式时限后收紧）
  3. 金标准覆盖率是字符二元组启发式指标，不等同医学评审；正式评分以赛方双评委为准
  4. 开发期用内网 qwen3.5-9b 做替身联调，qwen3.8-27b 的表现以赛前抽样联调为准（已通过 10 例真实病例）
  5. 数据集中 21 例原文自带诊断性描述（如影像报告结论），此类病例的覆盖指标偏高，报告中单独标注

10. 时间线与复现

  • 11-06 项目起步，定基线与校验框架
  • 11-08 仓库初始化，整合基线 + v3 校验入 main

  • 11-10 staged 流水线全量落地（62 项测试）合入 main
  • 11-11 导师数据集接入，真实数据压出 3 类硬伤并修复

  • 11-13 端点上下文容量事故复盘（每槽 4k → 80k/4 并行根治）；通宵全量压测
  • 11-14 02:58 全量压测收官（1293/1337）
  • 11-15 44 例失败复盘与提取盲区修复；规则符合性自动检查收尾

复现只需三步：

测试为纯标准库 unittest，收官时 90 项全部通过。

这个项目教会我最多的一件事：给 LLM 的任务，难点往往不在”让它写出来”，而在建立一套能证明它没瞎写的机制——可溯源的 evidence、单一来源的红线定义、带反馈的重试闭环，以及愿意逐例复盘失败的耐心。
